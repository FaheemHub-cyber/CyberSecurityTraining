Comprehensive security guidelines for software engineers, devops, and cloud architects. Learn secure coding, OWASP top risks, secrets management, and automated security testing.

Engineering Policies

1. Secure Development Lifecycle (SDLC) Policy

Security requirements integrated into every sprint and release phase.

  • Security gate requirements in sprint planning & design phase.
  • Mandatory Threat Modeling (STRIDE) for high-risk architecture changes.
  • Automated SAST & DAST quality gates blocking vulnerabilities in CI/CD.
  • Code review checklist: input validation, permission checks, logging.

2. Dependency & Supply Chain Policy

Mitigating third-party library and package risks.

  • Software Composition Analysis (SCA) active in all repos (Dependabot/Snyk).
  • Strict package version pinning and checksum verification.
  • Vulnerability threshold: Zero high/critical CVEs allowed in release builds.
  • Formal security approval required for new open-source dependencies.

3. Secrets Management Policy

Zero tolerance for hardcoded keys, API tokens, or credentials.

  • No secrets in source code, configuration files, or docker images ever.
  • HashiCorp Vault or Cloud Secret Manager required for secret storage.
  • Ephemeral secret usage: credentials expire and rotate automatically within 24 hours.
  • Pre-commit hooks (git-leaks) enabled on all developer machines.

4. API Security Policy

Securing microservices and external endpoint exposure.

  • OAuth2 / OpenID Connect (OIDC) authentication for all service endpoints.
  • Strict server-side input validation using allowlists and schemas.
  • Rate limiting and request throttling enforced at the API Gateway.
  • Output encoding and proper HTTP security headers on all API responses.

5. Infrastructure as Code (IaC) Policy

Hardening cloud configurations prior to deployment.

  • Terraform/CloudFormation security scanning (Checkov/tfsec) in pipelines.
  • Strict Principle of Least Privilege for IAM roles and service accounts.
  • VPC network segmentation, private subnets, and zero public S3 buckets.
  • Immutable infrastructure principles: replace instance rather than SSH patch.

Engineering Security Theory

OWASP Top 10 Deep Dive

Primary web application vulnerabilities and mitigations.

  • A01 Broken Access Control: Enforce server-side authorization checks for every object access.
  • A02 Cryptographic Failures: Protect data in transit (TLS 1.3) and at rest (AES-256).
  • A03 Injection: Use parameterized queries (prepared statements) for all database operations.
  • A04 Insecure Design: Perform threat modeling before writing code.
  • A05 Security Misconfiguration: Disable unused features, default accounts, and detailed stack traces.

OWASP API Security Top 10

Top vulnerabilities specific to modern APIs.

  • API1 IDOR (Broken Object Level Authorization): Validate user permissions against requesting user ID on every record lookup.
  • API2 Broken Authentication: Implement robust token validation and anti-brute-force controls.
  • API3 Broken Property Authorization: Prevent mass assignment and over-posting vulnerabilities.
  • API4 Unrestricted Resource Consumption: Set execution timeouts and rate limits.

OWASP LLM / AI Security

Securing AI models and LLM integration.

  • LLM01 Prompt Injection: Treat user prompts as untrusted input; isolate system prompts.
  • LLM02 Sensitive Info Disclosure: Sanitize training data and RAG context windows.
  • LLM03 Excessive Agency: Limit LLM agent autonomous tool capabilities and require human verification.
  • LLM04 Supply Chain Risks: Verify third-party model weights and datasets.

Secure CI/CD & Testing

Shifting security left into pipelines and UI automation.

  • Integrate SAST, DAST, container image scanning into Pull Requests.
  • Artifact signing (Cosign) to prevent build tampering.
  • UI Automation Security Assertions: Verify security headers (CSP, HSTS) and error stack suppression in Playwright/Cypress functional test suites.

Zero Trust Architecture

Never trust, always verify internal machine traffic.

  • Enforce Mutual TLS (mTLS) for microservice-to-service communication.
  • Network micro-segmentation using Service Mesh (Istio/Linkerd).
  • Apply Least Privilege to service accounts and cloud container roles.

Real-World Engineering Scenarios

Scenario 1: SQL Injection Discovery during Code Review High Severity

During a Pull Request review, you notice code building a query like: "SELECT * FROM users WHERE email = '" + req.body.email + "'".

Impact: Database compromise, authentication bypass, full data exfiltration.

Fix: Refactor to parameterized queries or ORM binding: db.query("SELECT * FROM users WHERE email = ?", [req.body.email]).

Prevention: Static code analysis (SAST) rules in CI/CD pipeline blocking raw string concatenation in SQL execution calls.

Scenario 2: AWS API Secret Key Committed to Repository Critical Severity

A developer accidentally commits a hardcoded AWS secret access key in a test script to GitHub.

Impact: Automated bot scanning discovers the key within minutes, launching unauthorized crypto-mining instances.

Fix: Immediately revoke/rotate the AWS key in AWS IAM. Purge commit history or delete repo access. Audit CloudTrail for suspicious activity.

Prevention: Mandatory pre-commit git hooks (git-leaks), use IAM Instance Profiles/Vault short-lived ephemeral tokens.

Scenario 3: Broken Object Level Authorization (IDOR) High Severity

An API endpoint GET /api/v1/orders/1042 returns order details. A user changes 1042 to 1043 and sees another customer's invoice.

Impact: Mass customer PII leak and unauthorized data access.

Fix: Add explicit authorization checks verifying order.userId === currentUser.id on the backend before returning data.

Prevention: Automated API security testing assertions and using non-sequential UUIDs for resource identifiers.

Scenario 4: Dependency Vulnerability (Log4j / Supply Chain Attack) Critical Severity

A critical Remote Code Execution vulnerability is disclosed in a deeply nested Java logging dependency used in production.

Impact: Total compromise of servers running the vulnerable library.

Fix: Upgrade the package version immediately or apply temporary JVM mitigations (-Dlog4j2.formatMsgNoLookups=true). Re-build and deploy.

Prevention: Automated Software Composition Analysis (SCA) alerts and strict dependency version controls.

Scenario 5: Excessive Agency in AI Agent Integration Medium Severity

An AI support bot integrated with an internal database plugin accidentally executes a `DROP TABLE` command after receiving a malicious user prompt.

Impact: Data deletion and service downtime.

Fix: Restrict AI agent database connections to read-only service accounts. Implement strict output verification filters.

Prevention: Apply Principle of Least Privilege to machine accounts and enforce human-in-the-loop approvals for destructive operations.
